| 需求 | 判定 | 关键决定项 |

| **需求1**：`uf_ht ⋈ vw_ekp_file_link` 里的文件，按原附件名导出 | **可实现，但 SQL 缺关键条件，现在无法定方案** | `vw_ekp_file_link` 的字段清单与 `v.on v.llssid` 之后的连接条件、`wdid`/`e9id` 语义 |

## 1. 需求1：`uf_ht ⋈ vw_ekp_file_link` 按原名导出

### 1.1 你给的 SQL 是不完整的（必须先补）

原话：

```sql
select wdid , e9id from uf_ht c left join vw_ekp_file_link v on v.llssid
```

问题在最后：**`on v.llssid` 后面没有比较对象**，语句在 `ON` 条件处断开。语法上不成立，无法执行。

从字段命名可以推测意图（**推测，未确认**）：

| 推测项 | 依据 | 需你确认 |
|---|---|---|
| `c` 是 `uf_ht`（合同建模表）的别名 | `from uf_ht c` | — |
| `v.llssid` 应等于 `c` 的某个主键 | `llssid` 字面像「**L**andray **L**ink **SS** **ID**」或「llss」是外部系统内部 id | **`v.llssid = c.???` 到底是哪个字段？** |
| `wdid` 是外部系统（蓝凌？）的文档 id | 命名习惯 | `wdid` 来自 `c` 还是 `v`？ |
| `e9id` 是 E9 侧主键 | 命名习惯，且需求2 要拿它当对外标识 | `e9id` 来自 `c` 还是 `v`？它与 `uf_ht.id` 是同一个值吗？ |

### 1.2 `vw_ekp_file_link` 是什么（关键未知项）

* **本工作区里没有这张表的任何定义**（已全库 grep：`vw_ekp_file_link`、`llssid` 均 0 命中）。
* 从名字看是**视图**（`vw_` 前缀），不是实体表。**视图没有自己的附件，它只是把附件元数据映射过来**。
* 「EPK」极可能是 **EKP（蓝凌 Landray）**。本工作区里 `ekpTest` 数据源已存在于多处代码，
  说明**这台 E9 曾经/正在对接蓝凌**：

  ```java
  // src/csj/fileDecode/LostFileDecode.java:110
  RecordSetDataSource ekpTest = new RecordSetDataSource("ekpTest");
  // src/csj/fileDecode/QueryTestCustomXiCen.java:138
  "select m.fd_model_id,m.fd_file_name,concat(m.fd_id,'_',f.fd_id) as fd_id,f.fd_file_path
     from SYS_ATT_MAIN m left join sys_att_file f on m.fd_file_id = f.fd_id
    where m.fd_model_id in (...)"
  ```

  → **蓝凌附件的元数据在 `SYS_ATT_MAIN`（主）+ `sys_att_file`（文件路径）两张表**，
  用 `fd_model_id`（业务文档 id）关联，`fd_file_name` 是**原文件名**，`fd_file_path` 是物理路径。
  `vw_ekp_file_link` 很可能是**这两张表再包一层、映射到 E9 合同的视图**。

**待确认（Q-L1）**：请提供 `vw_ekp_file_link` 的建视图 SQL 或字段清单。没有它无法确定
「附件 id 字段叫什么」「文件名取自哪一列」「物理路径是否可用」。

### 1.3 ⚠ 决定性风险：附件到底存在 E9 还是存在蓝凌？

这决定整个方案走哪条路，**必须先问清**：

| 情形 | 附件实体在哪 | 取文件的办法 | 本工作区是否有先例 |
|---|---|---|---|
| **A. 附件在 E9**（`vw_ekp_file_link` 只是关联表） | E9 `imagefile` | `ImageFileManager.getInputStream()` | ✅ 有（024 补丁包 `BatchDownZip`） |
| **B. 附件在蓝凌**（视图只给 fd_file_path） | 蓝凌服务器磁盘 `/home/resource/...` | `new File(path)` 直读 + 可能需 `DecryptFile.decryptFile1()` | ✅ 有（`csj/fileDecode/` 下 11 个类全是这个套路） |
| **C. 两边都有**（迁移期） | 混合 | 需按来源分流 | ⚠️ 无先例，最麻烦 |

`csj/fileDecode/` 那批类的注释写得很明确：

```java
// 原文件加密时，返回的文件路径：/home/resource/2023/11/4/18bfa97f8d70d364be880344f529b331
// 原文件未加密时，返回的文件路径：/home/resource/2023/11/4/18bfa97f8d70d364be880344f529b331_DecryptWkj
decryptFile = DecryptFile.decryptFile1(srcFile);
```

→ **蓝凌的文件是加密存的**，必须过 `com.system.file.decrypt.DecryptFile` 解密才能得到真文件
（`src/sysfiledecrypt-encrypted` 已在 IDEA 模块依赖里）。

> 所以需求1 最可能的技术路线是**情形 B**：读蓝凌视图 → 拼 `/home/resource + fd_file_path` → 解密 → 按 `fd_file_name` 导出。

### 1.4 「按原名导出」的落点选择

导出到哪儿，三种形态差别很大：

| 形态 | 说明 | 适用 |
|---|---|---|
| **① 打包 zip 流式下载** | 用户点按钮 → 浏览器拿一个 zip，内部是原文件名 | 人工导出、量小（与 024 补丁包一致，可直接复用其思路） |
| **② 落盘到服务器某目录** | 跑一次任务，把文件铺到 `/home/xxx/<原名>` | 批量迁移、给下一个系统消费 |
| **③ 直接推给三方** | 不落盘，取流后转手推走 | 其实就是**需求2** |

> 需求1 若是①，**前端仍需一个入口**（查询列表按钮或页面扩展 JS）。
> 若是②，做成 `BaseCronJob` 定时任务即可，无前端。
> **这一项你没说，必须确认（Q-L2）。**

### 1.5 重名怎么办（沿用前一份评估的结论）

**原 024 补丁包的做法是「静默覆盖」，不能照抄。** 而本工作区 `csj/fileDecode/` 那批类已经有一套
**可用的去重写法**，比 024 好得多：

```java
// src/csj/fileDecode/LostFileDecode.java:72-84
int counts = 0;
File newFile = new File(fileBefore.getFileName(counts));
while (newFile.exists()) {          // 重名就试下一个序号
    counts++;
    newFile = new File(fileBefore.getFileName(counts));
}
// getFileName(0) → name_<fd_id>.ext
// getFileName(n) → name(n)_<fd_id>.ext          ← 括号序号
```

**但它有两个问题**：
1. 用 `exists()` 先判后写，**仍是竞态**（两个进程同时跑会撞）；
2. 它靠 `_<fd_id>` 保证基本不重名 —— **一旦去掉 fd_id（你要求「原附件名称」），就会频繁撞名**。

→ 新类应改成 `Files.createFile()` 原子创建 + 捕获 `FileAlreadyExistsException` 递增，
并且**序号形态要你确认**（`(1)` / `_1` / 时间戳 / 加 e9id）。见 §3 的 Q-N1。

### 1.6 需求1 的候选方案（等确认后二选一）

**方案 L-A：导出为 zip 下载（有前端）**

```
查询列表按钮 → Servlet
  1. 执行你说的 SQL（补完整）→ 得到 (wdid, e9id, 附件路径/附件id) 结果集
  2. 逐个取流：
       情形 A → ImageFileManager.getInputStream()
       情形 B → DecryptFile.decryptFile1(new File("/home/resource" + fd_file_path))
  3. 按原文件名落临时目录（重名加序号）
  4. ZipOutputStream(UTF-8) 打包 → 流式响应 → 清理
类数：1（入口 Servlet）+ 复用底座 = 2
```

**方案 L-B：落盘导出（无前端，定时任务）**

```
BaseCronJob
  1. 同上查 SQL
  2. 同上取流 + 解密
  3. FileUtils.copyFile 到目标目录，按原名/序号命名
  4. writeLog 记录成功/失败清单（便于重跑）
类数：1（CronJob）+ 复用底座 = 2
```

**推荐 L-B 若目的是「把数据搬走」，推荐 L-A 若目的是「让人下载」。**
从你的措辞「**原附件名称导出即可**」看，更像 L-B（程序行为，不是交互），但需确认。

## 2. 需求2：建模表附件字段 → 以 e9id 传给另一系统

### 2.1 需求原文的关键歧义

> 查询 指定建模表里的指定附件字段 **或** 关联查询逻辑，通过 e9id 传输给另一个系统

这里有三个不确定点：

| # | 歧义 | 需确认 |
|---|---|---|
| 1 | 「**或**」是指两种数据来源（直接取字段 / 走关联查询）**二选一可配**，还是指「字段 + 关联一起用」？ | Q-P1 |
| 2 | `e9id` 是**传给对方的业务主键**（对方据此找自己的单子），还是**文件名的一部分**（`e9id_原名.pdf`）？ | Q-P2 |
| 3 | 「另一个系统」是哪个？**接口形态是什么**？ | Q-P3（最关键） |

### 2.2 对方接口形态决定方案（这是最大分叉）

| 形态 | E9 侧要做什么 | 类数 | 备注 |
|---|---|---|---|
| **HTTP/JSON（REST）** | Hutool `HttpRequest` POST，附件 Base64 或 multipart | 1 | 最常见，最好写 |
| **HTTP 上传文件（multipart）** | Hutool `.form(name, file)` | 1 | 大文件友好 |
| **中间库（对方轮询）** | INSERT 到中间表，文件 Base64 或路径 | 1~2 | 无网络依赖，有幂等位 |
| **WebService（SOAP）** | 手写 SOAP 客户端（**不生成 Axis 桩**） | 1~2 | 需 WSDL 的命名空间 + 操作名 |
| **FTP/SFTP 放文件 + 调接口通知** | 先传文件，再调一个通知接口 | 1~2 | 大附件首选 |
| **对方来 E9 拉** | E9 只需**发布一个查询/下载接口** | 1 | 这时是 BE-API 场景，不是 push |

> 路由把 BE-API 列为**候选**，正是因为「也可能反过来是对方来拉」。
> **这一点不定，代码 skeleton 都写不准。**

### 2.3 幂等：需求2 最容易被忽略、上线后必炸的点

**和 024 补丁包不同，推送类需求必须做幂等。** 场景：

* 定时任务跑了一半失败 → 重跑 → **已推过的又推一遍**，对方库里出现重复附件；
* 人工点两次按钮 → 重复推送；
* 流程回退重走节点 → 重复推送。

**建议做法**（成本很低，必须做）：

* 建一张**推送日志表**（或复用一张现成的中间表），字段至少：
  `e9id / 附件标识 / 目标系统 / 状态(0未推 1成功 2失败) / 推送时间 / 失败原因 / 文件md5`
* 每次推前按 `e9id + 附件标识` 查，已成功则跳过；
* 失败留痕，可重跑（**只补推状态 != 1 的**）。

> 若对方系统本身按 `e9id` 做了覆盖式接收，也不能省这张表 ——
> 你需要它来回答「到底推没推过」这个运维问题。

### 2.4 需求2 的候选方案

**方案 P-A：E9 主动推（push）**

```
触发点（三选一，需确认）：
  ① 流程 Action（流程到某节点自动推）
  ② 计划任务 BaseCronJob（定时扫未推的）
  ③ 建模查询列表按钮（人工触发）    ← 与需求1 的按钮形态一致

  1. 查建模表指定附件字段（或按关联查询 SQL）→ 得到 附件标识 + e9id
  2. 用底座取流 + 原文件名
  3. 组装报文（按对方接口契约）
  4. 调对方接口（Hutool / 中间库 INSERT / FTP）
  5. 写推送日志（成功/失败 + md5）
  6. 失败不阻断（Action 场景）或留待重跑（CronJob 场景）

类数：1 入口 + 1 底座 = 2
```

**方案 P-B：E9 发布接口，对方来拉（pull）**

```
发布 JAX-RS @Path 接口（单个类）：
  GET /api/custom/.../attachment?e9id=xxx
    → 按 e9id 查出附件 → 返回 {code,message,data:{fileName, fileBase64}} 或直接文件流
类数：1（不依赖底座也可，但建议复用）
```

**选 P-A 还是 P-B，完全取决于对方系统是「我们推给你」还是「我来你这儿取」。**
