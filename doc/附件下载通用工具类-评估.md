# E9 附件下载通用工具类 —— 现状反编译 + 可行性评估

| 项目 | 内容 |
|---|---|
| 评估对象 | `上海卓然工程技术SHZRGCJSecology20211230-024.zip` 的 `ecology/classbean` |
| 补丁包 KB 基线 | `9.00.2104.04`（`packagedescription/upinfo/024.properties`），测试报告记录客户版本 `9.00+ KB900210404` |
| 本次目标 | 吸收该补丁包「批量打包下载」的实现经验，设计一个**通用附件下载工具类**：传入附件 id 或附件路径即可下载，并支持「原名 / 加后缀」两种命名策略 |
| 分析方式 | `javap -p -c -constants` 静态反编译 + 包内配置手册/测试报告交叉验证 |

| 结论 | 该能力**需二开**，预算 **1 个类**；原实现可复用其「链路思路」，但**不建议照抄代码**（有 4 类硬伤，见 §6） |

## 2. classbean 两个类的职责

| 类 | 类型 | 职责 |

## 3. BatchDownZip 执行链路（还原）

### 3.1 入参（3 个，全部来自 request）

| 参数 | 含义 | 备注 |
|---|---|---|
| `ids` | 勾选的建模数据 id 列表，逗号分隔 | 对应查询列表（`mode_customsearch`）勾选行的 `id` |
| `fjname` | 附件字段**数据库列名**，可用逗号分隔多个 | 配置手册里写「红色附件字段名根据实际情况维护附件字段数据库字段名」 |
| `customid` | 查询列表 id（`mode_customsearch.id`） | 前端由 `ModeList.getCustomID()` 取 |

### 3.2 建模表名解析（先查表，不拼串）

```sql
select tablename from workflow_bill
 where id = (select formid from mode_customsearch where id = ?)   -- 参数化
```
→ 得到 `uf_xxx` 建模表名。**这一步是正确的写法**（没有凭 `modeid` 硬拼表名）。

### 3.3 临时目录（两套：解压目录 + zip 目录）

```
base   = SystemComInfo().getFilesystem()          // 附件存储目录配置
if (base == "") base = GCONST.getRootPath() + "formmode" + File.separatorChar

srcDir = base + "downloadBatchTemp" + sep + userid + currentDateTime + sep
zipDir = base + "downloadBatchTemp" + sep + userid + currentDateTime + "_zip" + sep
```

`userid` = `HrmUserVarify.getUser(req,resp).getUID()`；
`currentDateTime` = `new SimpleDateFormat("yyyyMMddHHmmss").format(new Date())`。

### 3.4 收集 imagefileid（**最容易踩错的语义**）

```
for (billid : ids.split(",")) {
    // 逐条查建模行（参数化）
    sql = "select id," + fjname + " from " + tablename + " where id = ?"
    for (col : fjname.split(",")) {
        value = row.getString(col)              // 附件字段值，多个逗号分隔
        if (value.isEmpty()) continue;
        // ★ 注意：字段值当 docid 用，不是 imagefileid
        sql = "select t.imagefileid from DocImageFile t where t.docid in (" + value + ")"
        // 结果逐个 append 到 imagefileid 拼接串（逗号分隔）
    }
}
```

> **这是本补丁包最需要继承的一条领域知识**：E9 建模表 / 表单里的「附件」字段，
> 存的值是 **`docid`（文档 id）**，不是 `imagefileid`。
> 附件实体要通过 `docimagefile`（`docid ↔ imagefileid` 关联表，`docfiletype=2` 表示附件）
> 才能过渡到 `imagefile` 表。新工具类若接受「附件 id」入参，必须明确是 `imagefileid` 还是 `docid`，
> 或两者都支持并自动判别（见 §7 待确认项 Q1）。

### 3.5 逐个附件取流落盘

对每个 `imagefileid`：

```sql
select * from imagefile where imagefileid in (<ids>)     -- 注意：这里是 String 拼接，非参数化
```

* 文件名：优先 `realname`，为空则退 `imagefilename`；
* 扩展名：取最后一个 `.` 之后，**转小写后重新拼回文件名**（统一小写后缀）；
* **office 文档特殊处理**：
  ```java
  if (isOfficeToDocument(ext) && isMsgObjToDocument()) {
      // ext ∈ {xls,doc,wps,ppt,docx,xlsx,pptx}
      // isMsgObjToDocument(): weaver_obj 配置 iWebOfficeClientName 含 "iWebOffice2003"
      //                       或 isHandWriteForIWebOffice2009 == "0"
      DBstep.iMsgServer2000 msg = new DBstep.iMsgServer2000();
      msg.MsgFileBody(rawBytes);            // 灌入 E9 里存的私有格式
      byte[] real = msg.ToDocument(rawBytes); // 转成真正的 Office 文件
      stream = new ByteArrayInputStream(real);
  }
  ```
  > E9 里 office 正文以 **iWebOffice 私有格式**落库，直接原样导出会得到打不开的文件。
  > 要拿真实文件必须过 `DBstep.iMsgServer2000.ToDocument`。**新工具类必须决定是否继承这一层**（见 Q7）。
* 取流方式（**正确做法，要继承**）：
  ```java
  ImageFileManager ifm = new ImageFileManager();
  ifm.getImageFileInfoById(Util.getIntValue(imagefileid));
  InputStream in = ifm.getInputStream();
  ```
  走 E9 的附件存储抽象，能自动覆盖「本地磁盘 / FTP / 阿里云 OSS / AES 加密附件」等存储形态。
  **千万不要直接读 `imagefile.filerealpath` 的物理路径**（工作区里 `src/csj/E10/MeetingArchiveToProjectAction.java:140`
  就是直读 `filerealpath` 的写法，一旦客户开了 FTP/OSS 存储或附件加密就会取不到文件）。
* 落盘：`fileCreate(dir, fileName)` —— 目录不存在则 `mkdirs()`；**目标文件已存在则先 `delete()` 再 `createNewFile()`**。
  **同名附件的处理方式 = 不做任何处理，静默覆盖（后写覆盖先写）**，详见 §3.5.1。

#### 3.5.1 同名文件究竟怎么被处理（字节码核对）

`fileCreate` 反编译还原（偏移 0~99）：

```java
public File fileCreate(String dir, String fileName) {
    File dirF  = new File(dir);
    File fileF = new File(dir + fileName);        // 偏移 12~31：直接原文件名拼路径

    if (!dirF.exists()) dirF.mkdirs();            // 偏移 36~47

    if (fileF.exists()) {                         // 偏移 48~54
        try { fileF.delete(); }                    // 偏移 57~62  ← 已存在就删掉
        catch (Exception e) { e.printStackTrace(); }   // 偏移 66~70
    }

    if (!fileF.exists()) {                        // 偏移 73~78
        try { fileF.createNewFile(); }             // 偏移 81~86
        catch (IOException e) { e.printStackTrace(); } // 偏移 90~94
    }
    return fileF;                                  // 偏移 97~99
}
```

**判定要点：**

1. **没有任何改名逻辑**。全类常量池 80 条 String 常量已逐条核对，**不存在** `_1` / `(1)` / `(2)` / 时间戳后缀之类任何用于去重的字符串。
2. `delete()` 的本意是兜底 `createNewFile()`（Java 中文件已存在时 `createNewFile()` 返回 `false` 并抛异常），
   **不是为了去重**；去重只是这个副作用。
3. 结果：**同名附件在磁盘上只剩最后一条，前几条已被物理删除**，zip 里也只有一个 entry。

| 场景 | 实际结果 |
|---|---|
| 2 个附件都叫 `合同.pdf` | 磁盘最终只有 1 个 `合同.pdf`，内容是**后处理那条**的 |
| 3 个同名附件 | 只剩 1 条，前 2 条被 `delete()` 掉 |
| zip 内 | 只有 1 个 entry，**压缩包内文件数 < 实际附件数** |

4. **「最后一条」是哪个不可预知**：`imagefileid` 列表的*构建*顺序是「先遍历 `ids` 行、再遍历 `fjname` 列」，
   但取数据用的是 `select * from imagefile where imagefileid in (<ids>)`，
   **`IN` 的返回顺序由数据库执行计划决定，不是 `IN` 列表里的顺序**。
   同一份数据在 SQLServer 与 Oracle 上可能留下**不同**的那一份。

> 原包测试报告 4 个测试点里没有构造同名附件场景，所以该缺陷未暴露。

### 3.6 打 zip

```java
new File(zipDir);                                   // 先建目录
String zipPath = zipDir + File.separator + currentDateTime + ".zip";
ZipOutputStream zos = new de.schlichtherle.util.zip.ZipOutputStream(
        new FileOutputStream(zipPath), "UTF-8");     // ★ 第三方 jar，指定 UTF-8 entry 编码
ZipDir.doZipDir(srcDir, zos, "");
zos.close();
```

用 **`de.schlichtherle.util.zip`** 而不是 JDK 自带 `java.util.zip`，唯一目的就是
**解决 zip 内中文文件名乱码**（JDK6/7 的 `ZipOutputStream` 不支持指定字符集）。
> JDK8 起 `java.util.zip.ZipOutputStream(OutputStream, Charset)` 已内置该能力，
> **新类可以不引入第三方 jar**（见 §8 关键决策 D2）。

### 3.7 ZipDir.doZipDir 还原（伪代码）

```java
public static void doZipDir(String dirPath, ZipOutputStream zos, String entryBase) {
    File dir = new File(dirPath);
    String entryName = "";
    if (dir.exists()) {
        for (File f : dir.listFiles()) {
            if (f.isDirectory()) {
                entryName = entryBase.isEmpty()
                        ? f.getName()
                        : entryBase + File.separator + f.getName();
                doZipDir(dirPath + File.separator + f.getName(), zos, entryName);
            } else {
                entryName = entryBase.isEmpty()
                        ? f.getName()
                        : entryBase + File.separator + f.getName();
                zos.putNextEntry(new ZipEntry(entryName));
                FileInputStream fis = new FileInputStream(f);
                byte[] buf = new byte[1024];
                int len;
                while ((len = fis.read(buf)) != -1) {
                    zos.write(buf, 0, len);
                }
                // ... closeEntry / 关流（反编译尾部被截断，按上下文为常规 finally 关流）
            }
        }
    }
}
```

> 缺陷：entry 名用 `File.separator` 拼接，**Windows 下是 `\`**，不符合 ZIP 规范（应为 `/`），
> 部分解压工具（macOS 归档工具、Linux `unzip`）会把整个路径当成一个文件名。
> 新类必须用 `/`。

### 3.8 流式响应（toUpload 三参版）

```
path = base + "downloadBatchTemp" + sep + userid + currentDateTime + "_zip" + sep + <responseFileName>
       ↑ 与 3.3 的 zipDir 拼接方式不完全一致（部分分支多一个 sep，见 §6 缺陷 W2）
```

```java
resp.setContentType("application/x-download");
String ua = agent;                       // ← 字段 agent 在本类中从未被赋非空值
if (!ua.contains("Firefox") && !ua.contains("Edge")) {
    // 旧 IE / Chrome 路线
    String v = new String(fileName.replaceAll("<","").replaceAll(">","")
                          .replaceAll("&lt;","").replaceAll("&gt;","")
                          .getBytes("UTF-8"), "ISO-8859-1");
    resp.setHeader("content-disposition", "attachment; filename=\"" + v + "\"");
} else {
    // Firefox / Edge 路线
    String v = URLEncoder.encode(fileName, "UTF-8").replaceAll("\\+", "%20");
    resp.setHeader("content-disposition", "attachment; filename=\"" + v + "\"");
}
// 8192 缓冲，BufferedInputStream → BufferedOutputStream 逐块 flush，不整体读入内存  ← 正确做法
```

下载文件名传的是 **`"批量下载.zip"`（字面量）**，实际落盘文件名 `currentDateTime + ".zip"` 只用于定位文件。
文件不存在 → `resp.sendRedirect("/login/BatchDownloadsEror.jsp")`（标准页，若客户环境无此页则 404）。

## 4. 时序总览

```
浏览器按钮
  └─ window.open('/weaver/weaver.formmode.apps.shzr.BatchDownZip?fjname=..&customid=..&ids=..')
       └─ BatchDownZip.doGet
            1. 鉴权取 userid、生成时间戳
            2. customid → workflow_bill.tablename（建模表名）
            3. 建 srcDir / zipDir（附件存储目录下 downloadBatchTemp/<userid><ts>[_zip]）
            4. ids × fjname → 建模行 → 附件字段值(docid) → DocImageFile → imagefileid 列表
            5. imagefileid → imagefile（realname/后缀小写）→ [office? iWebOffice 转换]
                            → ImageFileManager.getInputStream() → 写 srcDir/原文件名
                            ⚠ 同名即 delete→createNewFile 静默覆盖，无去重（§3.5.1）
            6. ZipDir.doZipDir(srcDir) → zipDir/<ts>.zip（schlichtherle，UTF-8）
            7. toUpload(resp, "批量下载.zip", <ts>.zip)  ← 流式 8KB 输出
            8. finally 删除 srcDir 与 zip
```

> 同名文件丢失发生在第 5 步，**到第 6 步打包时已经无法察觉**：`ZipDir` 只是遍历磁盘上现存的文件，
> 被覆盖掉的那几条在第 5 步就已经没了。所以「压缩包内文件数 < 勾选附件数」这个现象，
> 排查时要去第 5 步找，不要怀疑 `ZipDir`。

## 5. 前端入口（配置手册给出，非 ecode）

配置手册《批量下载附件配置手册 (1).docx》的做法是**查询列表页面扩展 JavaScript**，不涉及 ecode 打包：

```javascript
function batchDown(){
    var customId = ModeList.getCustomID();
    var ids = ModeList.getCheckedID();
    if (ids == "") {
        window.antd.message.error("请至少勾选一条数据！");
        return;
    }
    window.open('/weaver/weaver.formmode.apps.shzr.BatchDownZip'
        + '?fjname=附件字段名&customid=' + customId + '&ids=' + ids);
}
```

* 触发点：查询列表 → 页面扩展 → 自定义按钮 → `batchDown()`
* URL 前缀 `/weaver/` + 全类名，是 E9 `classbean` 目录下 Servlet 的直接访问方式
* `fjname` 需替换为该列表实际附件字段的**数据库列名**

测试报告（工单 1543034）4 个测试点：按钮显示、未勾选提示、多选打包下载、压缩包内附件可正常预览 —— 结论「通过」。

> 新工具类若改为**纯后端 API**（不直接对浏览器输出流），这段前端逻辑可完全复用，只需换 URL。

## 6. 原实现问题清单（新类必须规避）

### 6.1 安全

| 编号 | 问题 | 位置 | 影响 |
|---|---|---|---|
| S1 | SQL 直接拼接 `ids` / `fjname` / `imagefileid` | 3.4 的 `DocImageFile ... in (value)`、3.5 的 `imagefile in (...)` | 注入风险；`fjname` 来自 GET 参数且未做列名白名单 → 可被用来查询任意列 |
| S2 | 无任何数据权限校验 | 全流程 | 只要构造 `customid` + `ids` 就能下载**别人无权限**的附件；E9 标准的文档权限体系被绕过 |
| S3 | 无 `ids` 数量 / 单文件大小 / 总量上限 | 全流程 | 一次勾 5000 行会打爆磁盘与内存（zip 在服务端组装） |
| S4 | `deleteFile(String)` 是 public 且参数直通 `new File(path).delete()` | 方法表 | 若被外部 Servlet 复用，存在任意文件删除风险 |
| S5 | `printStackTrace()` 到处用（`doGet` 1 处、`fileCreate` 2 处、`toUpload` 2 处） | 多处 | 无审计轨迹，异常信息泄漏到容器日志 |

### 6.2 健壮性

| 编号 | 问题 | 说明 |
|---|---|---|
| W1 | **同名附件静默覆盖** | `fileCreate` 遇已存在文件直接 `delete()` + `createNewFile()`，**无任何改名/去重逻辑**。两个不同附件同名时**后者物理覆盖前者，压缩包内文件数少于实际附件数，且无日志提示**；「哪条活下来」还取决于数据库 `IN` 的返回顺序（见 §3.5.1） |
| W2 | 路径拼接不一致 | `doGet` 拼 `base + "downloadBatchTemp" + sep + userid...`；`toUpload` 在「`getFilesystem()` 非空且以 sep 结尾」分支里拼成 `base + "downloadBatchTemp" + sep + sep + userid...`（**双分隔符**）。`getFilesystem()` 恰好以分隔符结尾时，`toUpload` 定位不到刚生成的 zip → 跳 `BatchDownloadsEror.jsp` |
| W3 | `agent` 字段恒为空 | 全类无 `getHeader("User-Agent")` 调用，`agent=""` → 永远走「非 Firefox/Edge」的 ISO-8859-1 分支 → **Firefox/Edge 下中文下载文件名乱码** |
| W4 | 异常吞掉继续 | 3.5 循环里捕获 `Exception` 后仅 `writeLog`，继续下一张；最终可能生成一个空 zip 或半成品 zip，前端无感知 |
| W5 | `zip` 目录先 `fileCreate` 一个 `xxx.zip` 空文件，再写 `xxx.zip` 同名文件 | 语义混乱，依赖 `fileCreate` 的「存在即删」行为兜底 |
| W6 | 无超时/并发控制 | 同一用户连点两次 → `userid+时间戳` 相同（同一秒）→ 两线程写同一目录/同一 zip，互相删文件 |

### 6.3 性能

| 编号 | 问题 |
|---|---|
| P1 | 建模行**逐条查**（N 次 SQL），附件字段逐列查，`imagefile` 再逐 id 查 → `O(行数 × 字段数)` 次查询 |
| P2 | 全部文件先落盘再打包 → 磁盘 IO 翻倍（写一遍 + 读一遍），大附件场景慢 |
| P3 | zip 在服务端组装，无法断点续传，用户中途取消后服务端仍跑完 |

### 6.4 兼容性

| 编号 | 问题 |
|---|---|

## 7. 是否需 E9 开发评估

### 7.1 覆盖矩阵

| 判定层级 | 能否覆盖「通用附件下载工具类」 | 依据 |
|---|---|---|
| 标准功能 | ❌ 不能 | E9 标准有「文档/流程单个附件下载链接」，也有「我的文档批量下载」页面，但都绑定具体 UI 场景；**没有**「给一个 `imagefileid` / 路径就返回文件流」的可编程入口 |
| 配置 | ❌ 不能 | 无对应配置项；查询列表按钮的 `batchDown()` 本身就要挂二开 Servlet |
| 低代码 | ❌ 不能 | 建模/表单设计器无法产出可被其它 Java 代码调用的下载方法；且「重名加后缀」这类命名策略无可配项 |
| 需二开 | ✅ **是** | 需 1 个 Java 工具类：封装「id/路径 → 流 / 落盘 / 命名去重」 |

**结论：需二开，预算 1 个类**（符合 `references/04-E9开发规范.md` §0 类文件数最小化，通用后端形态上限 1）。

### 7.4 关键设计决策（相对原实现的改进）

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | 取流统一走 `ImageFileManager.getImageFileInfoById(id) + getInputStream()`，**禁止直读 `filerealpath`** | 兼容 FTP / 阿里云 OSS / AES 加密附件；工作区现有 `MeetingArchiveToProjectAction.java:140` 直读路径属于反例 |
| D2 | zip 用 **JDK8 原生** `new ZipOutputStream(os, Charset.forName("UTF-8"))` | 摆脱 `de.schlichtherle.util.zip` 三方依赖，中文名照样不乱码 |
| D3 | zip entry 分隔符固定 `"/"` | ZIP 规范，跨平台解压正确 |
| D4 | 临时文件放 `System.getProperty("java.io.tmpdir")` 下的专用子目录，**不放进附件存储目录** | 原实现往 `getFilesystem()`（附件盘）里写 `downloadBatchTemp`，污染附件存储、可能被附件清理策略误删、也可能被 Web 目录遍历直接下载 |
| D5 | 命名去重用**原子化** `Files.createFile(path)` 捕获 `FileAlreadyExistsException` 后递增序号（`名称(1).ext` / `名称(2).ext`） | 原实现 `exists()→delete()` 既是竞态，又会**静默丢文件**（§3.5.1）；原子创建才能既保证不覆盖、又保证并发安全 |
| D6 | `Content-Disposition` 用 **RFC 5987**：`filename*=UTF-8''<pct-encoded>` 同时保留 `filename="<ascii>"` 兜底 | 一次性覆盖所有浏览器，不用靠 `User-Agent` 分支（原实现 W3 就是因为 `agent` 恒空而失效） |
| D7 | 全部 SQL 参数化；`fjname` 之类「列名」入参改为**字段 id 白名单校验**（或改为调用方传 `RecordSet` 已取好的值） | 消除 S1；列名无法参数化，只能白名单 |
| D8 | 日志统一 `weaver.general.BaseBean#writeLog`（消息 + 异常双写），禁 `printStackTrace()` / slf4j | 技能硬口径 |
| D9 | 权限：默认要求调用方显式传入并校验 `User`，或提供「不做权限校验」的显式重载并在 Javadoc 标注 | 消除 S2；工具类不能假设调用场景 |
| D10 | office 文档 iWebOffice 转换做成**可选开关参数**（默认关闭），不硬编码 | 原实现 C2 强制依赖 `DBstep`；很多场景（如从三方系统 XML 拿附件）附件不是 iWebOffice 格式，强转会损坏文件 |

## 8. 待确认清单（请连同完整需求一起回答）

| # | 问题 | 为什么必须问 |
|---|---|---|
| Q1 | 「附件 id」指 **`imagefileid`** 还是 **`docid`**，还是两者都要支持？ | 决定要不要过 `docimagefile` 关联表；原包里面向的是 `docid`（建模字段值语义），与你说的「附件 id」可能不是一回事 |
| Q2 | 「附件路径」是 `imagefile.filerealpath` 这种**物理路径**，还是调用方自己手里的**绝对路径**？ | 决定要不要拼 `GCONST.getRootPath()`、要不要处理 FTP/OSS（此时物理路径根本不存在） |
| Q3 | 「增加文件后缀」具体规则？①重名才加（`报告.pdf` → `报告(1).pdf`）②始终加时间戳（`报告_20250101120000.pdf`）③加业务单号（`报告_HT2025001.pdf`）④**按 `imagefileid` 加**（`报告_12345.pdf`，绝对不重名且可反查） | 直接决定 `NamePolicy` 枚举形态；**注意原包完全没有去重，这是纯粹新增能力，没有可继承的既定规则** |
| Q3b | 同名且**内容相同**（同一附件被勾了两次）时，要不要去重成一个？还是也加后缀？ | 与原包行为差异最大的一点：原包会覆盖，新类若改成加后缀，会得到两个内容一样的文件，用户可能认为「重复下载」 |
| Q4 | 输出形态：直接写 `HttpServletResponse`（浏览器下载）／返回 `InputStream` 给调用方（如推三方、存中间库）／落盘到指定目录？**需要几种？** | 决定类里要有几个 public 方法；也决定要不要依赖 servlet-api |
| Q5 | 是否需要**批量打包 zip**？若需要，批量上限多少、zip 名规则？ | 决定要不要带 zip 逻辑（原包的核心，但你这次描述只提到单个附件） |
| Q6 | 调用场景有哪些？（流程 Action / 建模查询列表按钮 / 计划任务 / 对外 API / JSP） | 决定鉴权方式：Action 里是 `request.getRequestManager().getUser()`，Servlet 里是 `HrmUserVarify.getUser(req,resp)`，API 里可能是 token |
| Q7 | 是否需要 **iWebOffice office 文档转换**（`DBstep.iMsgServer2000.ToDocument`）？客户是否启用了 iWebOffice 正文？ | 决定是否引入 `DBstep` 依赖；不开则 office 正文类附件导出后打不开 |
| Q8 | 是否需要下载计数（`imagefile.downloads`）/ 下载日志（`DownloadLog` 表）？ | 原包有但全是死代码；若要，得确认客户 E9 版本有 `DownloadLog` 表 |
| Q9 | 调用方如何拿到 id？附件字段值语义在你们客户的 E9 上实测是 `docid` 还是 `imagefileid`？ | 这是 §3.4 的坑，不同版本/建模配置可能不同，**必须实测确认，不能照抄** |
| Q10 | 目标 E9 版本 / KB 号？（能否用 JDK8 的 `ZipOutputStream(OutputStream, Charset)`、`java.nio.file.Files`） | 决定 D2/D5 是否可用；若客户还在 JDK7 需回退 |
| Q11 | 数据库方言？（SQLServer / Oracle / MySQL / PostgreSQL / 达梦 / 金仓 / 信创） | 本需求 SQL 很少，但若做「按 docid 批量查附件」会用到 `in (...)` 长度限制（Oracle 1000 上限），方言必须确认 |
